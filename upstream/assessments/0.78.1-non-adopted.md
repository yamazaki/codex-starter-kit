# Upstream 0.78.1 不採用判断

## 位置付け

この文書は、`claude-code-starter-kit` 0.78.1、commit `f8f8ef5964c83cec2a5aaf84847a85149c96f6d4` で、Codex版へ変換しなかった機能、command、Skill、repository automationの詳細な判断記録である。

`DROP` は未調査を意味しない。また、将来にわたる永久的な禁止でもない。現在のCodex仕様、本プロジェクトのreview-first方針、初回releaseのscopeで採用しないことを表す。機械可読な採否の正本は `porting/feature-map.json`、`porting/command-map.json`、`porting/skill-map.json` とする。

## Claude専用のため変換しなかったもの

### `codex-plugin`

- upstreamの処理: Claude CodeからCodexを呼び出すpluginとsetupを提供する。
- 非採用理由: Codex自身を配布先とする本プロジェクトでは呼び出し方向が逆であり、当初要件でも再実装対象外である。
- 再評価: なし。将来、別製品間連携が必要になった場合は本starter kitとは別案件にする。

### `native-file-tools`

- upstreamの処理: Claude Code内部flagでnative file toolsの挙動を切り替える。
- 非採用理由: Codexに同じflag契約がなく、目的だけを推測して互換機能を作るべきではない。
- 再評価: Codexに対応する公開仕様が追加された場合のみ再調査する。

### `no-flicker`

- upstreamの処理: Claude CodeのTUI描画に関する内部設定を調整する。
- 非採用理由: Claude Codeの表示実装に固有であり、Codexの設定として移植できない。
- 再評価: Codexに同等の公開設定と具体的な利用者課題がある場合のみ再調査する。

### `statusline`

- upstreamの処理: Claude固有のstatusLine payloadを使い、状態やrate-limit情報を表示する。
- 非採用理由: payloadと表示契約がClaude固有である。Codexに存在しない互換statuslineを独自実装しない。
- 再評価: Codexが公開statusline APIを提供した場合に別設計する。

## global Hookとして採用しなかったもの

### `biome-hooks`・`prettier-hooks`

- upstreamの処理: `Edit|Write`後のPostToolUse HookでJS・TS系ファイルを検出し、Biomeの`check --write`またはPrettierの`--write`を実行する。
- 非採用理由:
  - 利用者の全repositoryへformatterを一律適用すると、repository固有のformatter、version、script、設定と衝突しうる。
  - PATH上のbinaryやstarter kit管理binaryを使うため、repositoryでpinした実行方法と一致する保証がない。
  - Hookによる追加変更がagentの編集後に発生し、差分の由来と検証範囲が分かりにくくなる。
  - upstream scriptはBash・`jq`前提で、そのままではcross-platform配布契約を満たさない。
- 現在の代替: 各repositoryのformatter、lint、verification commandを優先する。global formatter Hookの代替実装を本キットが提供しているわけではない。
- 再評価: repository内設定の検出、repo-localにpinされたcommand、明示opt-in、Windows fixtureを備えたoptional componentとしてなら検討できる。

### `doc-blocker`

- upstreamの処理: `SUMMARY`、`REPORT`、`FINDINGS`、`ANALYSIS`、`NOTES`、`RESULTS`、`TAKEAWAYS`を含む`.md`・`.txt`の書き込み時に、PreToolUse Hookで確認を要求する。既知の文書pathはallowlistで除外する。
- 非採用理由:
  - filenameだけでは、不要な一時文書と正式成果物を区別できない。
  - upstreamのallowlistはClaude用pathと特定の文書構造を前提とする。
  - global規則にすると、正式に`REPORT.md`等を使うrepositoryでも確認が発生する。
  - `Write`以外の編集経路を含むCodexの実際のfile tool契約へ再設計しない限り、保護範囲が一貫しない。
- 現在の代替: global代替は実装していない。必要なrepositoryでは、project `AGENTS.md`に文書作成方針を定義する。
- 再評価: filename patternとallowlistを利用者が設定でき、Codexの全対象編集経路を検証できるoptional componentとしてなら検討できる。

### `doc-size-guard`

- upstreamの処理: `AGENTS.md`が150行、`CLAUDE.md`が250行を超えた場合、PostToolUse Hookで非blocking警告を出す。
- 非採用理由:
  - 固定行数はrepositoryの複雑さ、生成規則、nested `AGENTS.md`を考慮しない。
  - upstream実装はproject root付近の特定pathと`Write` eventを前提とし、Codexの全編集経路やnested構成を網羅しない。
  - global警告は正当な長文文書でも継続的なノイズになりうる。
- 現在の代替: 行数制限の代替実装はない。progressive disclosureは設計原則として採用しているが、repository verifierは利用者projectの150行制限を検査しない。
- 再評価: 明示opt-in、設定可能な閾値、nested `AGENTS.md` discovery、非blocking結果を備えた`doc-hygiene` componentの候補とする。

### `feature-recommendation`

- upstreamの処理: kit更新時に新しいfeature・pluginを検出して`~/.claude/.starter-kit-pending-features.json`へ保存し、SessionStart Hookで名称・説明と`/update-kit`への案内を表示する。
- 非採用理由:
  - Codex版はupstream変更をscan、判断、releaseしてから利用者へ届けるため、未採用機能をsessionごとに推薦しない。
  - Codex版にはpending feature fileを生成する自動更新経路がなく、通知readerだけを移植しても入力がない。
  - session contextへの定期通知より、release notesとreviewable update planを正本にする。
- 現在の代替: upstream ledger、README、release notes、dry-run planで変更内容を確認する。
- 再評価: downstream配布元と新機能の選択更新機構を実装する場合に、通知方法を含めて再設計する。

### `pr-creation-log`

- upstreamの処理: Bashで`gh pr create`を実行した後、stdout・stderrからGitHub PR URLを抽出して表示する。
- 非採用理由:
  - Codexの通常workflowでは、作成したPRをtaskへ紐付け、review UIやGitHub連携で扱えるため、URL再表示の価値が小さい。
  - CodexのPR連携は、任意の外部terminalで実行された`gh pr create`を常に捕捉する仕組みと完全同一ではないが、本キットがglobal Bash監視を追加するほどの不足ではない。
  - upstream HookはBash command文字列とGitHub URL形式に依存する。
- 現在の代替: CodexのPR artifact・review workflowと、`gh pr create`自身が返すURLを利用する。
- 再評価: Codex外で作成されたPRの自動取込みが明確な利用要件になった場合に検討する。

### `tmux-hooks`

- upstreamの処理: tmux paneや長時間commandに関するreminderをHookで表示する。
- 非採用理由: tmuxを使わない利用者にもglobal設定を配ることになり、Codexのbackground terminal・task進行表示と責務が重複する。
- 再評価: tmux利用者向けの独立optional componentとして具体的な需要がある場合に検討する。

## 外部runtime・環境として採用しなかったもの

### `fonts`・`ghostty`

- upstreamの処理: fontやGhostty terminal環境を導入・設定する。
- 非採用理由: Codexのagent設定ではなく、OS・terminalの外観と利用環境に属する。starter kitのinstall対象を越える。
- 再評価: しない。必要な場合は各製品の導入手順を利用する。

### Skill `web-content-extraction`

- upstreamの処理: `defuddle`、`jsdom`、`pdfjs-dist`、`undici`を含むNode runtimeでURL・HTML・PDFから本文を抽出する。
- 非採用理由: 大きな依存runtime、network access、SSRF対策、package更新責任を本キットが持つことになる。一般的なweb調査はCodex native web searchへ委譲する。
- 注意: native web searchとlocal HTML・PDF抽出runtimeは完全同一ではない。後者が必要なprojectではproject-local toolとして導入する。
- 再評価: native機能で満たせない具体的な抽出要件と、runtime保守を引き受けるscopeが定まった場合に検討する。

### `web-content-update`

- upstreamの処理: SessionStart時に非同期でnpm registryを確認し、`web-content-extraction`の`defuddle`、`jsdom`、`pdfjs-dist`、`undici`を最大24時間ごとに更新する。`npm install --ignore-scripts`後にtestし、失敗時はlockfileとpackageをrollbackする。
- 非採用理由:
  - 更新対象の`web-content-extraction` Skill自体を配布していない。
  - session startでnetwork accessとpackage・lockfile変更を行い、同じkit versionでも実行時期により依存が変わる。
  - review-first、versioned release、再現可能な配布方針と合わない。
- 再評価: `web-content-extraction`を採用する場合でも、session start自動更新ではなくreleaseで依存を固定する。

### command `spec-kit-init`

- upstreamの処理: GitHub Spec Kitの`specify-cli`を`uv`等で導入・更新し、`specify init --integration claude`でproject-localなSDD workflowを生成するためのガイドである。Spec Kit本体をbundleするcommandではない。
- 非採用理由:
  - Spec Kitは独立した外部CLI・開発方法論であり、全Codex利用者に必要な基礎機能ではない。
  - upstream commandはClaude integrationを前提とし、Codex対応、command、生成物、versionを現在の公式仕様で再評価する必要がある。
  - `.specify/`、多数のSkills、spec文書をprojectへ追加するため、利用者の明示的な採用判断なしにstarter kitへ統合しない。
  - 外部CLIのrelease追随を本キットのcore保守責任にしない。
- 現在の代替: 必要なprojectで公式手順に従ってSpec Kitを直接導入する。本キットや別のbootstrap kitを介する必要はない。
- 再評価: 最新の公式仕様とlicenseを確認した上で、installを自動実行しない独立optional Skillとして検討できる。

### Skill `project-guidelines-example`

- upstreamの処理: project固有Skillを作るためのexample・templateを提供する。
- 非採用理由: 実行時能力ではなく、各projectの事情に合わせて作る雛形である。汎用user Skillとして配布すると、exampleと実規則の境界が曖昧になる。
- 再評価: project scaffold機能を別途提供する場合にtemplateとして検討する。

## 初回release scopeとして採用しなかったもの

### CI・Dependabot

- upstreamの処理: GitHub Actionsでtest・ShellCheck・web extraction検証を実行し、Dependabotで依存更新を管理する。
- 非採用理由: 初回releaseではlocal verifierを正本とし、公開repository・GitHub Actions・branch protectionの運用方針を決める前にCI設定をコピーしない。
- 再評価: repository公開後、required checks、runner OS、権限、Dependabot運用を決めた時点で設計する。

### MDM配布

- upstreamの処理: 組織管理端末へstarter kit設定を配るための検出・install・期待値生成を提供する。
- 非採用理由: 初回releaseのscopeに対して、組織policy、管理権限、端末差異、support責任が過大である。
- 再評価: 組織配布の具体的な利用者、管理方式、support範囲が決まった場合に別案件とする。

## 判断の要約

| 区分 | 現在の判断 | 将来の扱い |
| --- | --- | --- |
| Claude内部flag・TUI・statusline・Claude→Codex plugin | DROP維持 | Codexの公開対応仕様が出た場合のみ再評価 |
| global formatter Hook | DROP維持 | repository-awareなoptional componentなら検討可能 |
| `doc-blocker` | DROP維持 | project AGENTSまたは設定可能なoptional component |
| `doc-size-guard` | DROP維持 | `doc-hygiene` optional component候補 |
| feature recommendation・PR log・tmux reminder | DROP維持 | 明確な不足と利用要件が出た場合に再評価 |
| web extraction runtime・自動dependency更新 | DROP維持 | project-local toolまたは固定releaseとして再評価 |
| Spec Kit | DROP維持 | 公式Codex対応を確認した独立optional Skill候補 |
| CI・MDM | 初回releaseではDROP | 公開・組織運用方針決定後に別設計 |
