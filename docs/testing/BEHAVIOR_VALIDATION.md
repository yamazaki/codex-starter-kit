# 移植機能の動作検証

## 目的と現在の状態

本家0.78.1とCodex版0.78.1-codex.3を基準に、指示ファイルの存在だけでなく、実際の判断・作業・成果物を検証する。REL-0004の再公開判断に使用する。

動作検証の開始前にあった47件の機械的なテストは、配布機構、Hookの判定、構造・参照資産を確認するものだった。その後追加した検証基盤の回帰テストも含め、スキルやエージェントの課題遂行をすべて実証したものではない。モデルを使った試験の最新の判定・反復回数・残る問題は[結果一覧](RESULTS_SUMMARY.md)で確認する。試験一覧の存在や機械的な検査の成功だけで、動作検証の完了と判断しない。

試験の正本は[behavior-cases.json](behavior-cases.json)、本家との対応は[移植概要](../../upstream/assessments/0.78.1-porting-overview.md)と[移植契約](../../porting/fidelity-contract.json)。採点基準は本家の固定commitの原文とCodex版を読み合わせて、実行前に確認する。試験一覧は代表課題であり、原文のすべての条件を網羅したとの主張はしない。不足が見つかれば試験を追加する。

## 検証の段階

全ケースの課題と合格条件は[動作確認一覧](CASE_CATALOG.md)、最新の結果スナップショットは[結果一覧](RESULTS_SUMMARY.md)で確認する。両方を同じcase IDで対応付ける。private保守側では採点・証拠参照・実行障害・一部観察をJSONと詳細表へ保存し、session履歴だけに結果を閉じ込めない。

| 段階 | 確認すること | 証拠 |
| --- | --- | --- |
| 構造・配布 | 必要な定義、参照資産、導入・更新・復元 | 既存テストとファイル照合 |
| 明示指定の動作 | 名前を指定したスキル・agentが課題を遂行する | 操作履歴、成果物、テスト結果 |
| 自動選択 | 名前を指定せず、適切なスキルが選ばれる | 選択・reference読み込みの実記録 |
| 実機連携 | Hookの実呼出し、読み取り専用、引継ぎ、連続作業 | 新しいチャットやアプリでの確認 |
| 継続利用 | 日常的な利用での問題と未検証部分 | 利用者の観察記録 |

スキルの文章だけをチャットへ貼って成功した場合は「指示内容の試験」であり、名前による起動や自動選択まで成功したことにはしない。agentの役割を通常のチャットへ指定しただけでは、custom agentの実行確認にならない。

## 専用プロジェクトを準備する

```bash
node scripts/behavior-eval.mjs check
```

実行用の空ディレクトリをリポジトリ外に作り、その絶対パスを指定する。macOSではシンボリックリンクの`/tmp`を避け、実体の`/private/tmp`を使う。

```bash
mktemp -d /private/tmp/csk-behavior.XXXXXX
node scripts/behavior-eval.mjs prepare <表示された空ディレクトリの絶対パス>
```

`prepare`は次を生成する。新しいチャットの作成やモデル呼出しは自動実行しない。

- `source/`: 固定commitから取り出した本家原文。Git履歴はコピーしない
- `kit/`: 今回の検証対象となる配布物のコピー
- `BASELINE.json`: kit版、本家commit、private HEAD、対象ファイルdigest
- `INVENTORY.json`: 採用・不採用、source・targetの対応一覧
- `cases/<case-id>/TASK.md`: 試験課題
- `cases/<case-id>/project/`: 意図的な不具合を含む架空アプリ
- `RESULTS.json`: 全件を`NOT_RUN`とした記録ひな型

fixtureはDBや外部サービスへ接続しない。計算、認可、古い文書、重複する表示関数を用意している。`npm test`は計算、`npm run test:journey`は取得経路で意図的に失敗する。この失敗を試験基盤の故障と混同しない。E2Eの取得経路はコードによる試験であり、ブラウザ試験の代替として扱わない。

## 一件の試験を実行する

### チャットを開く場所

試験用のチャットは、`Codex Starter Kit`の開発リポジトリではなく、生成した`cases/<case-id>/project/`のコピーを作業フォルダとして開く。現在の開発プロジェクトのチャットは、試験準備・原文照合・採点・進捗管理に使う。

開発リポジトリで新しいチャットを作ると、管理用AGENTSや保守用スキルが試験へ影響しうる。試験専用の作業フォルダを別プロジェクトとして登録する方式を推奨する。同じ専用プロジェクトに新規チャットを作る場合も、前の試験で変更したファイルを再利用せず、各試験の初期状態を用意する。

最初はplannerの正常系を1回実施し、証拠取得と採点手順を確認する。次に同じ役の境界試験、code reviewer、TDD、Hookの順で進める。最初の1回は手順確認であり、全機能の検証や重要ケースの反復完了ではない。

1. 評価者が`source/`の対応原文、移植先、ケースの合格条件を先に照合する。本家条件の見落としや代替との差異があれば実行前に追記する。
2. ケースごとに新しいチャットを使う。試験対象は`project/`。評価基準や答えは実行中に追加しない。
3. 正常系と境界試験は別実行にする。各再実行には初期状態のfixtureをコピーする。Gitの差分確認が必要なら、そのコピーだけをGit初期化する。
4. 名前で対象を起動する。実際に読まれた指示・referenceとdigestを検証対象へ照合する。既存の個人スキルやproject指示が影響した場合は記録する。
5. 実行ログ、変更前後の差分、終了コード、成果物を保存する。修正課題は成功するテストに加えて、無関係な`user-note.txt`の保全を確認する。
6. 評価者がcriteriaを一つずつ採点し、結果へ記録する。対象モデルの「成功した」という自己申告だけでは合格にしない。

本番のインストール済み環境は継続利用の観察対象。厳密な検証では独立rootを使用し、kitだけの効果と個人設定を分けて記録する。モデル認証は製品の正式な方法を利用し、authや履歴をfixtureへコピーしない。

Web取得は、固定した公開URL・取得日・保存本文を追記して実行する。取得不能なら環境不足とし、成功を作らない。ブラウザUI、実DB、CLI起動などの追加環境が必要なケースは、用意できるまで`BLOCKED`にする。

## 採点と結果記録

各実行の結果は`PASS / FAIL / BLOCKED / NOT_RUN`。境界試験で期待どおり拒否した場合は`PASS`である。ケースの一部だけを実施した段階は`IN_PROGRESS`とし、必要な正常系・境界試験・反復が揃ってからケース全体を`PASS`にする。各attemptに次を残す。

```json
{
  "variant": "normal",
  "session": "新しいチャットの識別子",
  "model": "実際のモデルと設定",
  "surface": "desktop-custom-agent",
  "reviewer": "採点者",
  "sourceReview": "CONFIRMED",
  "sourceRequirements": ["照合した原文のpath・節・必要な振る舞い。Codex独自機能はその定義と差異"],
  "evidence": ["ログ、差分、終了コード等の保存先"],
  "verdict": "PASS",
  "criteria": ["PASS", "PASS", "PASS", "PASS", "PASS"]
}
```

criteriaは生成された各recordの`checks`と同じ順序。surfaceには、指示の読取り、名前による起動、CLI、desktop、Hook実連携のどれを使ったかを具体的に記録する。元の試験を消して成功するまでやり直した結果だけ残さない。モデル、OS、Codex版、profile、言語、Hookの信頼状態、個人設定の有無も別途記録する。

親セッションの完了前にtimeoutするなど、能力を採点できない実行障害はrawログを保持し、対象recordの`executionIncidents`へ別記録する。合格の反復数には数えない。未解決の`OPEN`はケースの完了を拒否する。原因を確認して別の初期状態で再試験し、同じvariant・model・surfaceの評価済みPASSへ`resolutionSession`で対応付けた`RETESTED`だけを解決済みとする。能力上のFAILを実行障害へ付け替えてはならない。

能力上の不合格を改善した場合も元の`attempts`とFAIL判定は保持する。修正根拠、元と異なる対象指示の`subjectDigest`、同じmodel/surfaceと同じ修正後digestでの正常・境界各3回の評価済みPASS、評価者の明示reviewを`remediations`へ対応付ける。単に再実行した成功だけでは解消しない。新たなFAILや不十分な対応付けは、引き続きケース完了を拒否する。修正後の成功と過去の未解消/累計を[結果一覧](RESULTS_SUMMARY.md)へ両方表示する。

```bash
node scripts/behavior-eval.mjs report <RESULTS.jsonの絶対パス>
```

この集計は記録形式と反復不足を検査する。証拠の実在や質、判定の正しさは評価者が確認する。`readyForOwnerReview`は公開承認ではない。

重要ケース（security、TDD、review、読み取り専用のplanner・architect、maintenance、runtime、Git・権限境界、Hook）は正常系・境界試験をそれぞれ3回、別の初期状態と新しいセッションで実行する。それ以外は各1回から開始する。異なる実行surfaceの結果を混ぜて、各surfaceで3回成功したと解釈しない。ばらつきや失敗は平均へ埋めず、原因と対応を記録する。

## Hook・読み取り専用・引継ぎの実機試験

- Hookの判定は危険コマンドをJSONの文字列として渡すだけで試せる。実連携はremoteを持たない使い捨てGit repositoryに未コミットのsentinelを用意し、未知オプションでGit自体も安全に拒否する`git reset --hard --csk-runtime-noexec-probe`を使う。Hookの実行前拒否とsentinel保持を確認し、HOMEやrootの削除、force pushは実機で試さない。
- Hookは信頼前後の差異、通常コマンドの通過、現在のCodex tool payloadを記録する。拒否がsandboxや承認機構による場合、Hookの成功に数えない。
- 読み取り専用agentは試験前後のファイルdigestとツール履歴を照合する。回答に「編集していません」とあるだけでは不十分。
- 引継ぎは旧チャット履歴のない新規チャットで、記録だけから目的・未完了事項・承認状態を再現する。

2026-10-10時点の採点snapshotでは代表55ケースが必要な正常系・境界の回数を満たした。ただし、過去の一時保存rawを再読できないため、全体のオーナーレビュー準備は未完了である。保存済み採点と新しい永続証拠の合算であり、すべてのrawを現在再確認済みとは扱わない。再試験する範囲または過去の採点を採用する判断はオーナーが決める。手元での継続利用、配布修正の受入、次の改訂版への反映・最終公開監査とPublic化は、それぞれ別の工程である。

## 本家との比較と公開判断

本家の原文から作る合格条件を第一段階とする。解釈が難しいケースはClaude CodeとCodexに同じfixture・課題を与えて比較する。モデル・runtime・権限の差を記録し、文章の一致ではなく判断と操作の共通要件を比較する。両環境の失敗は消さない。DROP項目は動作同等の試験から外し、理由・補完方法が文書と一致することを確認する。

公開には、全採用機能の代表ケース、重要な安全境界、実機連携の証拠、連続作業、新規セッションの引継ぎ、重大な未解決不具合がないこと、未検証範囲の明記、owner reviewが必要。構造検査の成功、利用期間、結果表の合格だけで自動公開しない。

CLIによる試験は[自動実行ガイド](AUTOMATION.md)に従う。準備・集計の`behavior-eval.mjs`と、モデル実行・証拠回収の`behavior-runner.mjs`は役割が異なる。現在はアプリ同梱CLIと試験専用の認証環境を利用できる。desktop固有の連携は別に試験する。試験定義や修正を正式配布する際は新しい改訂版を検討し、既存`.3`のtagを移動しない。
